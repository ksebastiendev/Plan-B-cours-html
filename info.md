Résumé — Bitcoin Protocol
Ce cours explique que pour vraiment comprendre Bitcoin, il faut lire Bitcoin Core, car dans Bitcoin, le code est la vraie spécification du protocole. La documentation et même certains BIP peuvent aider, mais au final, c’est le comportement du code accepté par le réseau qui fait foi.
1. Pourquoi lire Bitcoin Core
L’idée d’ouverture du cours est simple : “Use the Source, Luke”.
Autrement dit, si tu veux comprendre Bitcoin en profondeur, tu dois aller à la source, c’est-à-dire au dépôt Bitcoin Core.
Le formateur insiste sur plusieurs idées :
dans Bitcoin, le code est la règle
si le réseau accepte un comportement du code, ce comportement devient la réalité du protocole
Bitcoin Core est la base pour comprendre non seulement Bitcoin L1, mais aussi ce qui se construit au-dessus, comme Lightning et d’autres couches
Il rappelle aussi que le dépôt est un gros monolithe C++ mature, optimisé et complexe. Donc l’objectif n’est pas de tout lire d’un coup, mais de savoir où regarder.
2. Le démarrage de Bitcoin Core
Le cours commence ensuite par le point d’entrée du programme.
Les fichiers importants ici sont :
src/bitcoind.cpp
src/init.cpp
src/kernel/chainparams.cpp
bitcoind.cpp est le point d’entrée principal du daemon.
init.cpp gère l’initialisation : arguments, démarrage des threads, checks de base, arrêt propre.
chainparams.cpp contient les constantes des réseaux comme :
Mainnet
Testnet
Regtest
C’est là qu’on trouve des éléments importants comme :
le genesis block
le hashMerkleRoot
le port par défaut
les paramètres propres à chaque réseau
3. Les transactions
Le cours passe ensuite à l’unité de base de Bitcoin : la transaction.
Le fichier clé est :
src/primitives/transaction.h
On y trouve les structures fondamentales :
COutPoint : référence à une sortie précédente via TXID + index
CTxIn : une entrée de transaction
CTxOut : une sortie de transaction
CTransaction : la transaction complète
L’idée importante est qu’une transaction dépense des sorties précédentes et crée de nouvelles sorties.
C’est la logique UTXO.
4. Bitcoin Script
Pour dépenser une sortie, il faut satisfaire les conditions du script.
Les fichiers importants sont :
src/script/script.h
src/script/interpreter.cpp
Bitcoin Script est décrit comme :
un langage à pile
non Turing-complet
volontairement limité
Le cœur de l’exécution est dans EvalScript, une grande logique d’interprétation des opcodes comme :
OP_CHECKSIG
OP_DUP
C’est ici que se joue la validation des conditions de dépense.
5. La sérialisation
Le cours insiste aussi sur la sérialisation, qui est centrale dans Bitcoin.
Fichier clé :
src/serialize.h
C’est là qu’on comprend comment les objets Bitcoin sont transformés :
en octets pour le disque
en octets pour le réseau
Le mot-clé important à retenir est :
READWRITE(obj)
Quand on voit ça dans le code, on est face à la mécanique de sérialisation de Bitcoin Core.
6. Les blocs
Après les transactions, le cours passe aux blocs.
Fichier clé :
src/primitives/block.h
Le bloc contient notamment son en-tête de 80 octets, avec :
nVersion
hashPrevBlock
hashMerkleRoot
nTime
nBits
nNonce
Cet en-tête est la partie critique utilisée pour le Proof of Work.
7. Les arbres de Merkle
Le cours explique ensuite comment les transactions d’un bloc sont condensées dans une seule racine : la Merkle Root.
Fichier clé :
src/consensus/merkle.cpp
Le principe :
chaque transaction produit un TXID
les TXID sont hachés deux par deux
le processus continue jusqu’à obtenir une seule racine
Cette structure permet de :
résumer toutes les transactions du bloc
prouver qu’une transaction appartient à un bloc sans télécharger tout le bloc
Point important :
si le nombre de transactions est impair, la dernière est dupliquée pour garder une structure binaire complète
8. Le Proof of Work et la difficulté
Le cours aborde ensuite la preuve de travail.
Fichier clé :
src/pow.cpp
Deux fonctions importantes :
CheckProofOfWork()
CalculateNextWorkRequired()
CheckProofOfWork() vérifie qu’un bloc respecte bien la cible de difficulté.
CalculateNextWorkRequired() gère l’ajustement de difficulté tous les 2016 blocs.
L’idée essentielle :
le hash du bloc doit être inférieur à une cible dérivée du champ nBits
9. La validation
Le cœur du protocole se trouve dans :
src/validation.cpp
C’est probablement le fichier le plus important du dépôt.
Trois fonctions majeures sont mises en avant :
AcceptToMemoryPool()
CheckBlock()
ConnectBlock()
AcceptToMemoryPool
Gère l’entrée d’une transaction dans le mempool.
CheckBlock

Le cours montre donc que la validation Bitcoin suit un pipeline progressif.
10. L’ensemble UTXO et le chainstate

FICHE DE RÉVISION — INTERNET STRUCTURE
1. Pourquoi ce cours est important
Comprendre Internet est essentiel pour un développeur Bitcoin, parce que Bitcoin repose sur l’infrastructure réseau.
Les erreurs de routage, les pannes, les détournements de trafic et les attaques réseau peuvent affecter directement les services Bitcoin.
Idée centrale
Internet est très décentralisé dans son infrastructure
mais les usages et les services web sont souvent centralisés

2. Internet n’est pas le Web
Il faut distinguer :
Le Web
Facebook
YouTube
Instagram
Shopify
Amazon
Google
Microsoft
Ce sont des services.
Internet
C’est le réseau mondial interconnecté composé de plus de 100 000 réseaux indépendants.
À retenir
Le Web peut être centralisé, mais Internet lui-même est structurellement décentralisé.

3. Origines d’Internet
Internet vient d’ARPANET, réseau de recherche et de défense américain.
Points clés
années 1970
universités + recherche + militaire
premier lien international vers le Royaume-Uni et la Norvège
certaines liaisons passaient déjà par satellite
56 kbps était alors considéré comme rapide
Ensuite :
séparation de la partie militaire
continuité du réseau académique
développement du backbone civil

4. TCP/IP et RFC
En 1983, Internet adopte TCP/IP.
TCP/IP
C’est la base du fonctionnement moderne d’Internet.
RFC
Les standards Internet sont décrits dans les RFC (Request for Comments).
Comparaison utile
Les RFC jouent un rôle comparable aux BIP dans Bitcoin.

5. NSFNET et ouverture commerciale
Ensuite, NSFNET relie les grandes universités, puis Internet s’ouvre progressivement à un usage commercial entre 1991 et 1995.
En 1995, le backbone public historique disparaît au profit d’acteurs privés.

6. BGP4 : fondation du routage moderne
En 1995, Internet adopte BGP4, le protocole de routage inter-réseaux toujours utilisé aujourd’hui.
Point clé à retenir
Le fonctionnement fondamental d’Internet a très peu changé depuis 1995.

7. Réseaux à commutation de circuits vs paquets
Commutation de circuits
Exemple : ancien téléphone.
chemin réservé de bout en bout
connexion maintenue tout le temps
si un maillon casse, tout tombe
Commutation de paquets
Internet fonctionne ainsi.
les données sont découpées en paquets
chaque paquet peut être acheminé indépendamment
si un chemin casse, le routage peut changer
Conséquences
meilleure résilience
meilleure utilisation des ressources
mais pas de garantie absolue de bande passante

8. Taille des paquets et MTU
La taille maximale typique d’un paquet IP sur Internet est souvent autour de 1500 octets.

9. Pourquoi Internet a été conçu comme ça
Le réseau devait pouvoir survivre à des coupures majeures.
Le mode paquet permet de rerouter autour d’une panne ou d’une destruction partielle de l’infrastructure.

10. Le backbone mondial : surtout des câbles
Contrairement à une idée répandue, la majorité des communications longue distance passe par des câbles sous-marins, pas par satellite.
Pourquoi
capacité immense
latence faible
coût bien meilleur
plus adapté au backbone mondial
Données citées
premier câble transatlantique : 1858
environ 550 câbles sous-marins en 2024
environ 1,4 million de km

11. Satellites et Starlink
Les satellites ne forment pas le cœur d’Internet.
Starlink
Starlink est surtout un fournisseur d’accès :
utilisateur ↔ satellite
satellite ↔ station sol
station sol ↔ Internet classique
Donc Starlink donne accès à Internet, mais ne remplace pas le backbone principal.

12. Blockstream Satellite

Important
réception surtout unidirectionnelle
utile pour recevoir la blockchain
pas équivalent à un accès Internet classique complet

FICHE DE RÉVISION — LIGHTNING NETWORK
1. Définition
Le Lightning Network est une solution de seconde couche (Layer 2) construite sur Bitcoin.
 Son objectif est de permettre des paiements rapides, peu coûteux et fréquents, sans inscrire chaque transaction directement sur la blockchain Bitcoin.

2. Pourquoi Lightning existe
Bitcoin on-chain a des limites :
peu de transactions par seconde ;


frais parfois élevés ;


confirmations plus lentes ;


peu adapté aux micropaiements.


Idée centrale
Au lieu d’écrire chaque paiement sur la blockchain :
on ouvre un canal de paiement ;


on effectue plusieurs paiements hors chaîne ;


on règle le résultat final on-chain.



3. Canal de paiement
Un canal Lightning est un canal entre deux participants qui verrouillent des fonds ensemble.
Fonctionnement
ouverture du canal avec une transaction Bitcoin on-chain ;


échanges multiples hors chaîne ;


fermeture du canal avec règlement final on-chain.


Avantage
On peut faire beaucoup de paiements avec seulement :
1 transaction d’ouverture ;


1 transaction de fermeture.



4. État du canal
Le canal possède un état qui indique la répartition actuelle des fonds entre les deux parties.
Exemple :
état 1 : Alice 500, Bob 0


état 2 : Alice 450, Bob 50


état 3 : Alice 420, Bob 80


À chaque paiement, on met à jour cet état.

5. Sécurité du canal
Le réseau doit empêcher qu’un participant publie un ancien état pour tricher.
Mécanisme
Si quelqu’un diffuse un ancien état :
l’autre peut le détecter ;


il peut utiliser une justice transaction ;


le tricheur peut perdre les fonds du canal.


Outils techniques
scripts Bitcoin ;


timelocks ;


asymétrie des chemins de dépense ;


pénalité en cas de fraude.



6. HTLC
HTLC = Hashed Timelock Contract
C’est le mécanisme utilisé pour sécuriser les paiements Lightning, surtout les paiements routés.
Rôle
Il garantit que :
soit tout le paiement réussit ;


soit tout échoue et chacun récupère ses fonds.


Éléments clés
hash


préimage


timelock



7. Préimage
Le préimage est un secret créé par le destinataire du paiement.
Utilité
le destinataire crée un secret ;


il en fait un hash ;


ce hash est mis dans la facture ;


quand le paiement est réclamé, le préimage est révélé ;


cela permet de débloquer les fonds tout au long du trajet.


À retenir
Le préimage permet l’atomicité du paiement.

8. Routage
Lightning permet de payer quelqu’un sans avoir un canal direct avec lui.
Exemple
Alice → Bob → Carol
Alice peut payer Carol via Bob.
Pourquoi Bob accepte
Bob reçoit :
de petits frais de routage.



9. Onion routing
Le routage Lightning protège la confidentialité grâce à l’onion routing.
Principe
Chaque nœud intermédiaire connaît seulement :
d’où vient le paiement ;


à qui il doit le transmettre ensuite.


Il ne connaît pas :
toute la route complète ;


forcément l’expéditeur final ;


forcément le destinataire final.


Effet
Plus de confidentialité que sur Bitcoin on-chain.

10. Les BOLTs
BOLTs = Basis of Lightning Technology
Ce sont les spécifications techniques du Lightning Network.
Rôle
Ils définissent les règles communes pour que les implémentations Lightning soient compatibles entre elles.
Exemples importants
BOLT 1 : protocole de base


BOLT 2 : gestion des canaux


BOLT 3 : transactions et scripts


BOLT 4 : onion routing


BOLT 7 : gossip protocol


BOLT 11 : invoices Lightning


BOLT 12 : nouveau format plus avancé



11. BOLT 11
Le BOLT 11 est le format classique des factures Lightning.
Il contient notamment :
le montant ;


le hash du paiement ;


des informations de routage ou de demande de paiement.


C’est aujourd’hui le format le plus utilisé.

12. BOLT 12
Le BOLT 12 est une évolution plus récente.
Intérêt
plus flexible ;


meilleur pour certains cas d’usage ;


encore en cours d’adoption.



13. Liquidité
La liquidité est l’un des concepts les plus importants dans Lightning.
Définition
Pour qu’un paiement passe, il faut que les fonds soient du bon côté du canal.
Deux types
Outbound liquidity : capacité à envoyer


Inbound liquidity : capacité à recevoir



14. Outbound liquidity
C’est la quantité de fonds qu’un nœud peut envoyer à travers un canal.
Si Bob n’a plus de fonds de son côté :
il ne peut plus transférer le paiement plus loin.



15. Inbound liquidity
C’est la capacité à recevoir des paiements.
Si tous les fonds sont déjà de ton côté du canal :
tu peux avoir du mal à recevoir davantage.



16. Pourquoi les paiements échouent parfois
Même si une route existe, elle peut échouer parce que :
le canal n’a pas assez de liquidité dans la bonne direction ;


le réseau ne connaît pas l’état exact de chaque canal ;


un nœud intermédiaire n’a pas assez de capacité.



17. Gossip protocol
Le gossip protocol permet aux nœuds de se partager des informations sur :
les canaux publics ;


leur capacité ;


les frais ;


les annonces.


Limite
On voit la capacité totale d’un canal, mais pas la répartition exacte des fonds entre les deux côtés.

18. Choix des routes
Le nœud doit souvent choisir une route selon des probabilités.
Il peut optimiser pour :
la probabilité de réussite ;


les frais ;


la vitesse.


Le réseau essaie plusieurs routes jusqu’à ce qu’une fonctionne.

19. Frais Lightning
Les frais Lightning sont généralement :
très faibles ;


liés au routage ;


payés seulement si le paiement réussit.


En cas d’échec normal :
pas de frais de routage payés.



20. Loop in / Loop out
Ce sont des services de gestion de liquidité.
Loop out
Tu envoies des fonds via Lightning et tu récupères l’équivalent on-chain.
Effet :
tu libères de la place dans le canal ;


tu récupères de l’inbound liquidity.


Loop in
Tu fais l’inverse :
tu déplaces des fonds on-chain vers Lightning.



21. Submarine swap
Un submarine swap est un échange entre :
fonds on-chain ;


fonds off-chain (Lightning).


C’est la mécanique technique derrière loop in / loop out.
Important
Le processus reste atomique grâce à :
HTLC ;


hash ;


préimage ;


timelocks.



22. Splicing
Le splicing permet de modifier la capacité d’un canal sans le fermer complètement.
Exemple
canal initial : 1 000 sats


après splicing : 100 000 sats


Intérêt
Ajouter ou retirer des fonds plus proprement.
Limite
Encore complexe à généraliser.

23. Watchtower
Une watchtower est un service qui surveille le réseau pour toi.
Rôle
Si quelqu’un publie un ancien état pendant que ton nœud est hors ligne :
la watchtower peut réagir ;


elle aide à protéger tes fonds.



24. Static Channel Backup
Le Static Channel Backup est un mécanisme de sauvegarde dans LND.
Important
Ce n’est pas l’état complet du canal minute par minute.
Il permet surtout de :
retrouver l’existence des canaux ;


demander leur fermeture propre pour récupérer les fonds.


Attention
Restaurer un ancien état complet peut être dangereux.

25. Pourquoi les backups Lightning sont compliqués
Lightning dépend d’un état très précis et récent.
Si on restaure un vieux backup :
le réseau peut croire à une tentative de triche ;


on risque une pénalité.



26. Nœud Bitcoin + nœud Lightning
Un nœud Lightning s’appuie sur Bitcoin.
Pourquoi exécuter son propre nœud Bitcoin
vérifier soi-même les transactions ;


ne pas dépendre d’un tiers ;


respecter le principe : don’t trust, verify.

Mini-résumé à mémoriser
Le Lightning Network est une couche 2 de Bitcoin qui permet des paiements rapides et peu coûteux grâce à des canaux hors chaîne. La sécurité repose sur les états de canal, les HTLC, les préimages et les pénalités contre la triche. Les grands enjeux sont la liquidité, le routage, les sauvegardes, l’UX et l’automatisation. Les BOLTs définissent les règles du protocole. 1. Internet Infrastructure

Ils échangent leurs routes grâce au protocole :

BGP fonctionne sur la confiance
BGP suit un modèle :
“trust, don’t verify”
Les routeurs annoncent simplement :
"Je peux atteindre ce réseau."
Les autres leur font confiance.
Internet fonctionne quand même parce que :

≈ moins de 10 000 opérateurs


La réputation maintient l’ordre.

Attaques BGP
Deux problèmes principaux :
Route leak
Annonce accidentelle de routes.
Exemple :
 Telecom Malaysia (2005)
 → 179 000 routes annoncées par erreur.

BGP hijack
Un attaquant annonce un réseau qu’il ne possède pas.
Pourquoi ça marche ?
Parce que BGP préfère toujours :
le préfixe le plus spécifique
Exemple :
/24 est préféré à /22.

Sécurité BGP
Solutions :
Max-prefix filtering
 Limiter le nombre de routes annoncées.
Bogon filtering
 Bloquer les IP privées.
RPKI
 Signer cryptographiquement les routes.

Anycast
Une même IP est annoncée depuis plusieurs endroits.
Exemple :
Google DNS
8.8.8.8
